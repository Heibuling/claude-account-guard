# 封禁归因六层模型

## 0. 先读这三条

1. **这份文档解释「哪些自身配置会让风险变高」，不解释「平台算法怎么运作」。** 平台的风控实现不公开，任何声称"精确命中封号阈值"的说法都不可信。
2. **不要用"让信号看起来一致"的方式解决问题。** 用代理修正 IP、用虚拟卡对齐 BIN、用指纹浏览器伪造设备——这些做法本身违反服务条款，是把"可能被误判"换成"确定违规"。本文所有处置动作都是"消除矛盾"，不是"伪造一致"。
3. **每条结论都带证据强度。** 申诉时只有 A 级证据有用；B 级只能用于自查排序；C 级不要写进申诉。

**证据强度分级**

| 级别 | 定义 | 典型材料 | 用途 |
| --- | --- | --- | --- |
| A | 平台或银行出具的、可核验的书面记录 | 账单/发票、订阅收据、订单号、官方邮件、账单地址证明 | 可直接用于申诉 |
| B | 你自己系统里可导出的客观记录 | 请求日志（含时间戳与时区）、设备列表截图、Key 轮换记录、CI 配置 | 用于自查与佐证，需脱敏后引用 |
| C | 口头描述、印象、"我记得" | "我一直在国内用"、"我没共享过" | 不要写进申诉正文 |

六层之间存在**关联放大**：同一设备、同一支付方式、同一出口 IP 上的多个信号会互相加权。这就是为什么"每项看起来都不严重"的账号也会被封，也是为什么第 5 层（第三方依赖）最危险——它一次性把网络、支付、使用模式三层绑在一起。

## L1 地区与网络层（对应评分卡 N1–N5）

### 1.1 信号

- 接入 IP 的归属国家/地区，以及它是否属于服务区域名单内。
- 注册地区、支付地区、常用接入地区三者之间是否矛盾。
- 同一会话中短时间内跨越多个大洲的 IP 变化（例如 10 分钟内从东亚跳到北美）。
- IP 类型：数据中心、住宅、移动网络、企业专线。类型频繁切换本身就是异常特征。
- 企业出口 IP 上还跑着多少其他账号（共享出口的"邻居污染"）。

### 1.2 平台如何观测

平台在每次请求里能看到的与网络相关的事实，主要来自这些层：HTTP 连接的对端 IP、TLS/HTTP 头、区域化的 CDN 与边缘节点选择、以及登录/注册/支付流程中提交的国家与地址信息。它们不需要"识别你"，只需要判断**这些事实彼此是否自洽**，以及**是否与历史行为一致**。

请记住一个现实：判断"是否自洽"的方法很多，但你没有能力让不一致的事实变成一致——你只能让真实情况变合规。

### 1.3 用户可自查项

| 检查项 | 怎么看 | 命中意味着 |
| --- | --- | --- |
| 注册地区是否在服务区域名单内 | 对照 <https://www.anthropic.com/supported-countries>（会变） | 不在名单内：任何技术手段都不改变"不合规"这一事实 |
| 日常接入 IP 国家 | `curl -s https://ifconfig.me` 或路由器/防火墙日志 | 与注册地/支付地不同 → 矛盾信号 |
| IP 类型是否稳定 | 检查是否在家庭宽带、公司专线、云主机之间来回切换 | 类型混用 → 异常特征 |
| 是否存在跨洲跳变 | 看 VPN/代理客户端日志、SSH 隧道、CI 出口 | 10 分钟内跨洲 → 强异常 |
| 企业出口是否独享 | 询问网络管理员：NAT 出口段有多少人、有没有别的 SaaS 账号共用 | 共享出口 → 邻居风险不可控 |

### 1.4 合规处置动作

1. 用**你真实所在的、名单内的地区**的网络接入；如果所在地不在名单内，不要"想办法接进去"，直接走 `third-party-risk.md` 第 6 节的合规替代路径。
2. 固定接入方式：不要为了"更快"在家庭宽带、公司网络、云主机、出差的酒店网络之间频繁切换同一账号。
3. 企业环境：向 IT 说明该账号的合规用途，争取独立出口或用云厂商通道（Bedrock / Vertex AI）承接 API 流量。
4. 移除所有"为了改 IP"而存在的组件：代理链、住宅代理、指纹浏览器、IP 轮换脚本。它们不是风险缓冲，是风险来源。
5. 记录你**真实**的网络环境（宽带运营商 + 城市、公司出口、出差行程），这是 A 级/B 级证据的基础。

### 1.5 证据强度

- A：公司网络出口说明（IT 出具）、云厂商资源所在地证明、机票/酒店行程（跨境办公场景）。
- B：路由器或防火墙的出口 IP 日志、CI 运行日志里的 runner 区域。
- C："我一直用同一个网络"——无日志支撑时不可用。

### 1.6 自查清单（勾选 = 风险存在 = 计 1 分）

- [ ] N1 账号注册地/使用地不在服务区域名单内，或接入 IP 与申报地区不符
- [ ] N2 接入 IP 国家与注册地、支付地不一致
- [ ] N3 同一会话内出现过短时间跨洲 IP 跳变
- [ ] N4 接入 IP 类型混用（数据中心/住宅/移动来回切换）
- [ ] N5 企业出口 IP 与他人共用，且无法说明边界

## L2 支付与身份层（对应评分卡 P1–P4）

### 2.1 信号

- 卡 BIN 所属国家、账单地址国家、接入 IP 国家三者是否一致。
- 卡片类型：一手信用卡、借记卡、预付卡、虚拟卡、礼品卡余额。
- 同一张卡是否被多个账号使用；同一账号是否频繁换卡。
- 是否存在争议退款（chargeback）、拒付、"未授权交易"申诉。
- 注册姓名、支付持卡人姓名、身份证明材料是否指向同一主体。

### 2.2 平台如何观测

支付是整条链路上信息最密集的一环：卡组织返回的 BIN 国家、发卡行、卡类型，账单地址（AVS 校验），3-D Secure 的验证结果，以及退款/拒付记录。这些数据由银行与卡组织提供，**不是平台自己推断的**，因此"伪造支付信息"在实践中几乎必然暴露，而且暴露方式通常不是"支付失败"，而是"支付成功但账号被标记"。

### 2.3 用户可自查项

| 检查项 | 怎么看 | 命中意味着 |
| --- | --- | --- |
| BIN 国家 / 账单国家 / IP 国家 | 对照银行 App 里的卡信息与账单地址；IP 用 ifconfig.me | 三者不一致 → 高权重矛盾 |
| 卡类型 | 银行 App 或卡面 | 预付卡/虚拟卡 → 支付层不可核验 |
| 是否多人共卡 | 问清楚谁在用这张卡订阅 | 共卡 → 账号天然关联 |
| 退款争议历史 | 银行账单里搜 "chargeback / dispute / 争议" | 有记录 → 风险极高，且难以解释 |
| 姓名一致性 | 注册姓名 vs 持卡人姓名 vs 证件 | 不一致 → 需要 A 级材料解释 |

### 2.4 合规处置动作

1. 用**本人名下、账单地址真实**的一手支付方式；不要用代付、代充、共享卡、虚拟卡。
2. 账单地址填写真实地址（与银行记录一致），不要为了"匹配 IP"去改地址。
3. 如果卡是家人的：让实际持卡人本人注册并订阅，或改用企业采购流程。
4. 有争议退款的，先与银行结清争议，再评估账号是否还值得继续投入；申诉时如实说明，不要编造。
5. 团队场景走 Team/Enterprise 的集中采购与成员授权，避免"一个人买、十个人用"。

### 2.5 证据强度

- A：银行对账单（可遮盖卡号后四位以外信息）、发票、订阅收据、账单地址证明。
- B：支付成功邮件、订单号、订阅管理页截图。
- C："这是我自己的卡"——若姓名或地址对不上，等于没有证据。

### 2.6 自查清单

- [ ] P1 卡 BIN 国家 ≠ 账单地址国家，或 ≠ 接入 IP 国家
- [ ] P2 使用预付卡 / 虚拟卡 / 多人共卡 / 代付
- [ ] P3 存在争议退款或拒付记录
- [ ] P4 注册姓名与支付姓名、身份证明不一致

## L3 账号使用模式层（对应评分卡 U1–U4）

### 3.1 信号

- 同一账号在多个地理位置同时在线。
- 设备数量、设备类型在短时间内大幅变化（今天 1 台，明天 6 台，分布在不同城市）。
- 会话被大量并发复用：同一 session 在多个 IP、多个客户端指纹下出现。
- 多账号关联：同一设备、同一支付方式、同一出口 IP、同一手机号绑定了多个账号。
- 登录与使用节律异常（例如 24 小时不间断、或集中在少数几分钟内爆发）。

### 3.2 平台如何观测

一次登录会同时产生：IP、User-Agent、时区/语言、设备标识（Cookie、localStorage、客户端实例 ID）、以及后续的请求节律。这些事实的组合比任何单一事实都更稳定——设备指纹变了但 IP 没变、IP 变了但 Cookie 没变，都是"同一个人换了环境"的正常表现；而"IP 在两地、Cookie 相同、请求并发"则是典型的共享凭据特征。

### 3.3 用户可自查项

| 检查项 | 怎么看 | 命中意味着 |
| --- | --- | --- |
| 谁在用这个账号 | 列出所有知道密码/授权过 OAuth 应用的人 | 有人共享 → 立即停止 |
| 设备与会话列表 | 账号设置里的登录设备/会话页 | 出现陌生城市/设备 → 凭据可能已泄露 |
| 是否多账号 | 自己数一遍：同一支付/设备/IP 下有几个账号 | 关联风险，一损俱损 |
| 第三方客户端 | 检查是否装了"共享号池"客户端、破解客户端、自动切换工具 | 凭据被第三方持有 |
| 请求节律 | 看 API/客户端日志的时间分布 | 24h 不停或突发爆发 → 被当成自动化 |

### 3.4 合规处置动作

1. 一人一号。需要多人使用就买 Team/Enterprise 的席位——这是唯一合规的"共享"。
2. 立即吊销所有不认识的会话，改密码，重新登录一次以刷新会话。
3. 关闭不用的 OAuth 授权与第三方应用。
4. 不要"多开小号分摊风险"：同一设备/支付/IP 上的账号是关联的，只会把单点故障放大成多点故障。
5. 团队场景用组织账号 + 成员角色，而不是把主账号密码发给同事。

### 3.5 证据强度

- A：Team/Enterprise 的席位与成员记录、组织管理员出具的说明。
- B：自己的设备列表截图、会话时间线、公司 VPN 分配记录。
- C："只有我自己用"——如果设备列表里出现三个城市，这句话反而有害。

### 3.6 自查清单

- [ ] U1 账号存在共享（含把密码给同事/朋友、共享号池客户端）
- [ ] U2 同时在线设备数量异常或波动巨大
- [ ] U3 同一支付/设备/IP 关联多个账号
- [ ] U4 会话被工具或第三方客户端大量并发复用

## L4 API 与密钥层（对应评分卡 K1–K5）

### 4.1 信号

- Key 出现在公开仓库、npm/PyPI 包、前端 bundle、移动端安装包、Docker 镜像层。
- Key 出现在 issue、PR 评论、CI 日志、报错截图、客服工单。
- 单个 Key 被多个主体使用（多个客户、多个下游、多个地理区域）。
- Key 无分级、无轮换、无吊销演练；一个 Key 跑遍开发/测试/生产。
- 调用量突增、异常并发、超出预算限额、错误率飙升（通常是泄露后的典型曲线）。

### 4.2 平台如何观测

API 请求天然携带元数据：Key 归属的工作区/组织、调用时间、来源 IP、模型、token 数量、错误类型。平台不需要"扫描你的代码"就能看到异常——它看到的是**一个 Key 的调用模式突然变成"由很多地方并发使用"**。而公开仓库泄露则来自外部：GitHub 等平台与安全厂商会持续扫描公开提交，泄漏的 Key 往往在分钟级就被自动化工具抓取并滥用。

### 4.3 用户可自查项

| 检查项 | 怎么看 | 命中意味着 |
| --- | --- | --- |
| 仓库里有没有 Key | `python scripts/audit.py --path .` | 命中 → 立即吊销 |
| git 历史里有没有 | `python scripts/check_history.py --path .` | 命中 → 密钥视为已泄露 |
| 前端/客户端是否含 Key | 搜构建产物、`app.asar`、`dist/` | 等于公开 |
| 是否分级 | 每个环境/服务是否有独立 Key | 一个 Key 全用 → 无法最小化损失 |
| 是否轮换 | 上次轮换时间、有无轮换记录 | 超过 90 天 → 卫生问题 |
| 用量是否异常 | Console 的用量与错误率曲线 | 突增 → 可能已泄露 |

### 4.4 合规处置动作

1. 吊销 → 换新 → 再从历史里清理。**顺序不能反**：先清理历史再吊销，中间那段时间别人仍可用。
2. 把 Key 移入密钥管理（环境变量注入、云 KMS/Vault、CI secret），永不进仓库。
3. 按环境/服务/团队成员拆分 Key，做到"能单独吊销、能单独限额"。
4. 建立 90 天轮换与离职即吊销的规则。
5. 对外分享日志/截图前先脱敏：`python scripts/redact.py -i log.txt -o log.redacted.txt`。

### 4.5 证据强度

- A：Console 的 Key 列表与轮换记录、吊销时间戳、CI secret 配置截图（值不可见）。
- B：请求日志（已脱敏）、误用告警记录、代码提交时间线。
- C："我从来没提交过"——历史扫描结果会直接推翻它。

### 4.6 自查清单

- [ ] K1 密钥出现在公开仓库、前端代码或客户端安装包
- [ ] K2 没有按环境/服务分级，无法单独吊销
- [ ] K3 超过 90 天未轮换
- [ ] K4 密钥写入过日志/截图/issue
- [ ] K5 调用量存在无法解释的突增

## L5 第三方依赖层（对应评分卡 T1–T4）

### 5.1 信号

- 项目配置里的 `base_url` / `ANTHROPIC_BASE_URL` / `proxy` 指向非官方域名。
- 使用"中转 API""镜像站""共享号池""合租""代充"等形态的服务。
- 上游账号池的出口 IP 与大量下游用户共用。
- 同一批上游凭据被多个下游同时使用，调用模式高度混杂。

### 5.2 平台如何观测（以及为什么你无法对冲）

中转服务的商业模型，决定了它必须**用有限的上游账号与出口服务大量下游用户**。于是它天然产生这些特征：单账号多地理位置并发、单凭据跨时区使用、调用量远超个人使用曲线、出口 IP 与注册/支付信息矛盾。

对平台来说，这些正是"账号被共享/被批量使用"的典型形态。对下游的**你**来说，后果是结构性的：

1. **你的请求以别人的身份发出。** 上游账号的合规状态决定你的可用性。
2. **你的 Key 在链路中被二次持有。** 中间层能看到明文请求（包括你发的内容）。
3. **上下游连带。** 上游账号被封，你的服务当天中断；而你连申诉要用的账号都不是你的。
4. **你无法审计上游。** 它是否留存日志、是否转售数据、是否转手给第四方，你没有任何验证手段。
5. **你无法自证。** 申诉需要"是我本人、用我自己的账号、在合规地区使用"，这三条你一条都不满足。

**结论：中转不是"省钱方案"，是把"成本"换成"封号概率 + 数据外流 + 无法申诉"。**

### 5.3 用户可自查项

| 检查项 | 怎么看 | 命中意味着 |
| --- | --- | --- |
| base_url 指向 | `python scripts/audit.py` 的 AG-020 | 已在使用中转 |
| 配置里的域名 | 搜 `base_url`、`ANTHROPIC_BASE_URL`、`proxy` | 逐条确认归属 |
| 服务商能否出具主体信息 | 官网有无公司主体、合同、发票 | 无主体 → 不可审计 |
| Key 的归属 | 在谁的控制台里？谁付钱？ | 不是你的 → 你不是账号主体 |
| 数据留存政策 | 有无 DPA/隐私条款/日志保留说明 | 没有 → 内容可能被留存 |

### 5.4 合规处置动作

1. 把 `base_url` 改回官方 endpoint；云上场景改用云厂商官方 endpoint（Bedrock / Vertex AI）。
2. 吊销所有经过中转的 Key（它们必须视为已泄露）。
3. 把中转期间的调用日志、账单、合同**留档**——如果将来需要解释"那段时间不是我本人在用"，这是唯一的凭证。
4. 迁移评估请按 `third-party-risk.md` 的清单逐项做，尤其是"计费主体"和"数据留存"两项。
5. 如果预算确实不支持官方定价：先评估替代模型（`third-party-risk.md` 第 6 节），而不是降低合规标准。

### 5.5 证据强度

- A：与官方或云厂商直接签订的合同/发票、云资源账单。
- B：迁移前后的配置文件 diff、Key 吊销记录。
- C："我只是图便宜"——这不是解释，是自证违规。

### 5.6 自查清单

- [ ] T1 存在中转/镜像/共享号池依赖
- [ ] T2 存在非官方、非云厂商的接入域名
- [ ] T3 第三方依赖不可审计（无主体、无条款、无发票）
- [ ] T4 云厂商通道的区域或计费主体不合规

## L6 内容与自动化层（对应评分卡 C1–C3）

### 6.1 信号

- 生成内容本身违反 Usage Policy（例如用于欺诈、冒充、大规模骚扰、违规内容生产）。
- 用脚本批量调用 consumer 端（网页/客户端）接口，模拟人类点击、绕过前端限制。
- 绕过或规避 rate limit（多 Key 轮换刷量、动态换 IP 分散请求、改 User-Agent 伪装客户端）。
- 自动化抓取平台内容（爬取对话、模型输出、站点数据）。

### 6.2 平台如何观测

平台看到的是请求形态：来源是否官方 SDK、节律是否符合人类操作、是否命中单账号的速率上限、内容是否触发安全分类器。自动化调用 consumer 端接口在协议层就有痕迹（缺前端必需的请求头、请求间隔过于均匀、并发远超人类操作）。

### 6.3 用户可自查项

| 检查项 | 怎么看 | 命中意味着 |
| --- | --- | --- |
| 用途是否合规 | 对照 Usage Policy 逐条自查 | 命中 → 停止该用途 |
| 是否脚本化 consumer 端 | 代码里有没有 Playwright/Selenium/Puppeteer 驱动 claude.ai | 违反条款 |
| 是否绕过限额 | 有没有多 Key 轮换、动态代理分散请求 | 违反条款 |
| 是否抓取 | 有没有爬虫/导出工具在跑 | 违反条款 |
| 是否伪装 | 有没有改 UA、伪造客户端版本、反检测补丁 | 违反条款 |

### 6.4 合规处置动作

1. 需要程序化调用 → 用官方 API（有明确 rate limit 与计费），不要自动化 consumer 端。
2. 需要更高吞吐 → 走官方提额流程或用云厂商通道，不要用"多 Key 轮换"绕上限。
3. 需要抓取数据 → 用平台提供的导出功能或官方数据接口。
4. 发现自己在做"对抗性"设计（伪装、轮换、规避），立即停止：这是被封禁最直接的原因之一，而且申诉时几乎没有解释空间。

### 6.5 证据强度

- A：官方 API 的调用记录、提额审批邮件、企业合同中的用量条款。
- B：代码仓库里"使用官方 SDK + 遵守 rate limit"的实现（可用于说明设计意图）。
- C：无。

### 6.6 自查清单

- [ ] C1 生成内容用途可能违反 Usage Policy
- [ ] C2 存在脚本化批量模拟人类交互或绕过 rate limit
- [ ] C3 存在自动化抓取/爬取行为

## 7. 六层如何互相放大

```
              ┌──────────────────────────┐
              │  L5 第三方依赖（放大器）  │
              └───────────┬──────────────┘
         ┌────────────────┼────────────────┐
         ▼                ▼                ▼
   L1 网络矛盾      L2 支付身份矛盾    L3 共享凭据
   (IP/地区)        (BIN/地址/姓名)    (多人多设备)
         └────────────────┼────────────────┘
                          ▼
                 ┌─────────────────┐
                 │ L4 密钥泄露      │  ← 让"别人的滥用"变成"你的责任"
                 └─────────────────┘
                          ▼
                 ┌─────────────────┐
                 │ L6 内容与自动化  │  ← 决定申诉还有没有空间
                 └─────────────────┘
```

- 只命中一层：通常是"可以用 A 级证据解释"的情况。
- 命中两层以上且互相独立：说明账号的"身份一致性"整体存疑，申诉难度显著上升。
- 命中 L5 或 L6：申诉空间很小，优先止损与迁移，而不是反复提交申诉。

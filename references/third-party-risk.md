# 第三方依赖风险评估

> 这是本知识库里最应该先读的一篇。中文圈里绝大多数"说不清为什么被封"的案例，都能追溯到这一层。

## 1. 什么算第三方依赖

| 形态 | 你看到的样子 | 实质 |
| --- | --- | --- |
| 中转 API | 一个域名，`base_url` 指向它，价格是官方的一半甚至十分之一 | 它用自己的上游账号代你请求，你的 Key 只是它的计费标签 |
| 镜像站 / 反向代理 | 长得像官方站点，功能少一些 | 同上，且可能记录你的对话 |
| 共享号池 / 合租 | 卖"Claude 账号使用权"，或按次卖额度 | 一个账号卖给 N 个人，你连账号都不是你的 |
| 代充 / 代付 | 帮你付订阅费 | 支付主体与使用主体分离 |
| 打包客户端 | 自带"加速"、自动切换节点、破解 UI | 客户端本身在替你改网络与设备特征 |
| 第三方 SDK / 网关 | 包装官方 API，附赠"负载均衡""多 Key 池" | 多 Key 池 = 共享号池 |

判断标准很简单：**请求最终由谁的账号发出？谁付钱给平台？** 如果不是你，你就在用第三方依赖。

## 2. 为什么它必然产生风险特征

中转的商业模型只有一条路能赚钱：**用有限的上游账号，服务尽可能多的下游用户**。这直接导致：

```
        ┌──────────────┐
下游 A ─┤              │
下游 B ─┤  中转服务商   ├── 上游账号 1（注册地 X，支付地 X）
下游 C ─┤  （1 个出口）  ├── 上游账号 2（注册地 Y，支付地 Y）
下游 D ─┤              │
        └──────────────┘
```

从平台视角看，这些上游账号表现出：

- 同一凭据在多个国家/时区并发使用；
- 调用量远超个人使用曲线（因为是几十上百人在用）；
- 出口 IP 与注册地/支付地矛盾；
- 请求形态混杂（不同 SDK、不同客户端版本、不同提示词风格）。

**这不是猜测，是数学**：一个账号卖给 50 个人，就会产生 50 个人的行为痕迹。你无法通过任何配置改变这一点——因为你不是那个账号的主体。

## 3. 你会失去的四样东西

| 失去的 | 具体后果 |
| --- | --- |
| **账号主体** | 上游账号不是你的。它被封，你当天中断；你想申诉，连账号都不是你的 |
| **凭据控制** | 你的 Key 在链路中被二次持有。它可以被记录、被转售、被拿去跑别的东西 |
| **内容控制** | 请求与响应经过第三方。它是否留存、是否用于训练、是否转给第四方，你无法验证 |
| **申诉资格** | 申诉需要"本人、本人账号、合规地区、可核验支付"四个要素。用中转时你一个都不满足 |

最后一条最致命：**你不是不能申诉，你是没有可申诉的事实基础。** 这也是为什么中转用户的典型结局是"账号没了、钱没了、连原因都说不清"。

## 4. 如果你正在评估（或已经被迫在用）

先做一张表，逐项填。填不出来的项，就是风险项。

| 项目 | 必须能回答 | 不能回答意味着 |
| --- | --- | --- |
| 服务主体 | 公司全称、注册地、官网、能否开发票 | 无法追责，也无法证明你是"善意使用" |
| 合同/条款 | 有无服务协议、数据处理协议（DPA）、SLA | 内容可能被留存或转售 |
| 日志政策 | 是否留存请求正文？保留多久？谁能访问？ | 假定全部留存 |
| 上游来源 | 它用什么账号、什么地区、多少用户共用 | 无法评估连带风险 |
| 计费与退款 | 发票主体、退款规则 | 出事后无法主张任何权利 |
| 退出成本 | 换回官方要改多少代码、多少数据要迁移 | 你会被锁定，越晚越难走 |
| 责任划分 | 上游被封时它承担什么 | 通常什么都不承担 |

**一个实用判据**：如果对方不能提供"书面 SLA + 数据处理条款 + 发票"，那么它提供的不是服务，是一个随时会消失的口子。

## 5. 成本要按 TCO 算，不是按单价算

| 成本项 | 官方/云厂商 | 中转 |
| --- | --- | --- |
| 单价 | 明码标价 | 低（看起来省 50%–90%） |
| 中断损失 | 有 SLA 兜底 | 上游一封，业务当天断 |
| 数据风险 | 有合同约束 | 内容经手第三方，不可审计 |
| 迁移成本 | 无 | 越晚越高 |
| 申诉可能 | 有 | 基本没有 |
| 合规审计 | 可出具 | 无法出具 |

**"省下的 90% 费用"往往在下一次中断或一次数据事故里一次性还回去**，而且还得加上"客户数据经手了不明第三方"这个无法向客户解释的问题。

## 6. 合规替代路径（按可行性排序）

1. **官方支持地区的正常接入**：人在名单内、用本人支付方式、走官方 endpoint。这是唯一"零解释成本"的路径。
2. **云厂商通道**：AWS Bedrock / Google Vertex AI。要求：① 使用该云厂商支持的区域；② 计费主体与合同主体一致；③ 不要把个人 consumer 账号与云上资源混用。企业场景优先选这条。
3. **企业版 / 团队版合规采购**：按席位购买，成员授权，发票齐全。适合"多人要用"的团队。
4. **本地可合法使用的替代模型**：如果所在地无法合规使用上述通道，"合规可用性优先于模型偏好"——选一个你所在地能合法使用、能开发票、有 SLA 的模型，把工程适配成本当成一次性投入。

> 不要把这四条理解成"退而求其次"。对大多数业务来说，**可预测的可用性 + 可审计的数据流** 比"某个模型强 5%"重要得多。

## 7. 迁移步骤（从今天开始）

```bash
# 1) 先把现状记录下来（这是你唯一的"善意使用"证据）
python scripts/audit.py --path . --report-dir ./guard-report

# 2) 找出所有指向第三方的配置
grep -rIn --exclude-dir=.git -E 'ANTHROPIC_BASE_URL|base_url|api_base|proxy' . | head -50
```

3. **吊销所有经过中转的 Key**（它们必须视为已泄露）。
4. 改 endpoint：把 `base_url` 指向官方或云厂商；删掉"多 Key 池""自动切换"这类逻辑。
5. 小流量灰度：先用一个非关键服务跑通，确认延迟、错误率、成本可接受。
6. 验证合规：确认计费主体、发票、区域都符合你的申报。
7. 留档：把中转期间的账单、合同、调用日志、迁移 diff 存进 `account-evidence/`。
8. 复算评分卡：T1–T4 应该归零。
9. 复盘：写清楚"为什么当初用了它、迁移付出了什么"，作为团队的决策记录。

## 8. 常见辩护，以及为什么站不住

| 说法 | 回应 |
| --- | --- |
| "它只是转发，不存内容" | 转发层必然能看到明文；"不存"是它的承诺，不是你的验证。你没有审计能力。 |
| "它比官方便宜 90%" | 便宜的部分来自哪里？共享上游账号 + 无合规成本。这两项恰恰是风险的来源。 |
| "它说自己有官方授权" | 要求出具书面授权与主体信息。拿不出来就是不成立。 |
| "我一直用，没出事" | 没出事不等于没问题：上游账号的处置是批量且滞后的，你只是在等。 |
| "我只是个人用，量很小" | 你的请求仍然以别人的身份发出；关联的是上游的整体行为，不是你的用量。 |
| "不用中转我就用不了" | 那就走第 6 节的替代路径。**用不了** 和 **违规用** 是两件事。 |

## 9. 自查清单

- [ ] 我能说出每一次调用最终落在哪个账号主体上
- [ ] 我的 `base_url` / `proxy` 只指向官方或合规云厂商
- [ ] 我的 Key 没有经过任何第三方链路（经过的都吊销了）
- [ ] 我用的是自己付款、自己持卡的账号，或组织席位
- [ ] 我保留了中转期间的合同/账单/日志（若曾使用）
- [ ] 我算过 TCO，而不是只看单价
- [ ] 我有迁移预案（改哪个配置、多久能切完）

## 10. 不要做的事

- 不要为了"稳定"去用多 Key 池、共享号池、合租账号。
- 不要相信"内部渠道""官方白名单""企业共享"这类话术。
- 不要用中转来"绕过地区限制"——这是双重违规（地区 + 共享），也是最快被封的组合。
- 不要在申诉里隐瞒曾使用中转：账单与请求日志会暴露它，隐瞒只会让解释更糟。

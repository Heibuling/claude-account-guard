# 风险评分卡

## 0. 它是什么，不是什么

- **是**：把 `ban-causes.md` 的六层信号压缩成 25 个可判定条目，让你知道"先修哪三个"。
- **不是**：平台的真实风控分。平台不公开算法，任何声称能"算出封号概率"的产品都是在猜。
- **前提**：所有条目都以"遵守服务条款"为解。**不要用伪造信息去把某个条目的答案改成"否"**——那只是把自查变成自欺。

## 1. 计分规则

| 维度 | 权重 | 条目 | 单项分值 |
| --- | --- | --- | --- |
| 网络一致性 | 25 | N1–N5（5 项） | 5 分/项 |
| 支付与身份一致性 | 20 | P1–P4（4 项） | 5 分/项 |
| 账号使用模式 | 15 | U1–U4（4 项） | 3.75 分/项 |
| API Key 卫生 | 15 | K1–K5（5 项） | 3 分/项 |
| 第三方依赖 | 15 | T1–T4（4 项） | 3.75 分/项 |
| 内容与自动化 | 10 | C1–C3（3 项） | 3.33 分/项 |
| **合计** | **100** | **25 项** | — |

**每项取值**：`1` = 风险存在（命中）；`0` = 风险已消除；`0.5` = 不确定 / 无法自查。

**未知不是免费**：不确定按半分计，因为"你不确定"本身就意味着这项没有被管理。把不确定项查清楚，是性价比最高的动作。

**维度得分** = 权重 ×（该维度命中值之和 ÷ 该维度条目数）
**总分** = 六个维度得分之和，四舍五入到 1 位小数。

## 2. 分档与行动

| 分档 | 区间 | 含义 | 必须优先处理的前三项 |
| --- | --- | --- | --- |
| 低 | 0–20 | 配置层面基本干净 | 1) 建立 90 天密钥轮换；2) 每季度复核第三方依赖；3) 确认 Team/Enterprise 席位与实际使用者一致 |
| 中 | 21–45 | 有可解释的矛盾点 | 1) 先补齐支付身份一致性（BIN/账单/IP/姓名）；2) 清掉所有中转或共享依赖；3) 轮换全部 Key 并做分级 |
| 高 | 46–70 | 多层矛盾叠加，解释成本高 | 1) 立即下线所有非官方 endpoint 与共享凭据；2) 吊销并重建全部凭据；3) 固化 A 级证据（账单、合同、日志）以备申诉 |
| 极高 | 71–100 | 结构性风险，接近"必然出事" | 1) 停止新增投入，按 `incident-response.md` 的 0–24h 清单止损；2) 评估合规替代路径；3) 不要再"多开账号" |

注意：**分档只决定优先级，不决定命运。** 低分账号也可能因为一次内容违规被封；极高分的账号也可能因为还没触发阈值而活着——但那是运气，不是安全。

## 3. 25 个条目的判定标准

### 网络一致性（25 分）

| ID | 条目 | 判"是"（=1 分）的标准 | 判"否"（=0 分）的标准 |
| --- | --- | --- | --- |
| N1 | 注册/使用地在服务区域名单内，接入 IP 属于该地区 | 接入 IP 国家 ≠ 账号申报国家，或所在地不在名单内 | 三者一致，且所在地在名单内 |
| N2 | 接入 IP 国家与注册地、支付地一致 | 任意两者不一致 | 三者一致 |
| N3 | 没有短时间跨洲 IP 跳变 | 24 小时内出现过跨大洲 IP 变化 | 近 30 天只有一个地理区域的出口 |
| N4 | 接入 IP 类型单一 | 数据中心/住宅/移动/企业专线中出现 ≥2 种 | 长期只有一种类型 |
| N5 | 企业出口独享或边界清晰 | 与其他团队/个人共用 NAT 出口，且无法说明 | 独享出口，或有明确的出口管理记录 |

### 支付与身份一致性（20 分）

| ID | 条目 | 判"是"（=1 分） | 判"否"（=0 分） |
| --- | --- | --- | --- |
| P1 | 卡 BIN 国家 = 账单地址国家 = 接入 IP 国家 | 任一不等 | 三者一致 |
| P2 | 本人名下的一手信用卡 | 预付卡/虚拟卡/他人卡/代付 | 本人一手卡，账单地址真实 |
| P3 | 没有争议退款或拒付 | 近 24 个月有 chargeback/dispute | 无 |
| P4 | 注册姓名 = 支付姓名 = 身份证明 | 任一不等 | 三者一致 |

### 账号使用模式（15 分）

| ID | 条目 | 判"是"（=1 分） | 判"否"（=0 分） |
| --- | --- | --- | --- |
| U1 | 账号仅本人使用 | 有人知道密码、共用号池、多人登录 | 仅本人，且开启了额外验证 |
| U2 | 同时在线设备数稳定合理 | 单日设备数波动 >3 倍，或出现陌生城市 | 设备清单可解释 |
| U3 | 没有多账号关联 | 同一支付/设备/IP 下有 ≥2 个账号 | 只有一个账号 |
| U4 | 会话没有被大量并发复用 | 同一凭据在多 IP/多客户端并发 | 单一客户端、单一会话 |

### API Key 卫生（15 分）

| ID | 条目 | 判"是"（=1 分） | 判"否"（=0 分） |
| --- | --- | --- | --- |
| K1 | 密钥从未进入公开仓库/前端/客户端 | 在仓库、历史、bundle、镜像层里出现过 | `audit.py` 与 `check_history.py` 均无命中 |
| K2 | 按环境/服务分级，可单独吊销 | 一个 Key 跑遍所有环境 | 每环境/服务独立 Key |
| K3 | 有轮换机制（≤90 天） | 无记录或超期 | 有轮换记录与负责人 |
| K4 | 密钥不在日志/截图/issue 中 | 出现过 | 有日志脱敏流程，分享前跑 `redact.py` |
| K5 | 调用量在设计限额内 | 出现无法解释的突增 | 用量曲线平稳，有预算告警 |

### 第三方依赖（15 分）

| ID | 条目 | 判"是"（=1 分） | 判"否"（=0 分） |
| --- | --- | --- | --- |
| T1 | 没有中转/镜像/共享号池依赖 | 任一存在 | 全部为零 |
| T2 | 所有接入域名属于官方或合规云厂商 | 出现第三方域名 | 仅官方/云厂商域名 |
| T3 | 第三方依赖可审计 | 无主体、无合同、无隐私条款 | 有主体、合同、DPA/隐私条款 |
| T4 | 云厂商通道区域与计费主体合规 | 区域不支持，或计费主体与合同不一致 | 区域支持且计费主体一致 |

### 内容与自动化（10 分）

| ID | 条目 | 判"是"（=1 分） | 判"否"（=0 分） |
| --- | --- | --- | --- |
| C1 | 生成内容用途符合 Usage Policy | 存在违规用途 | 用途可对照条款说明 |
| C2 | 没有脚本化模拟人类交互或绕 rate limit | 存在 | 程序化调用走官方 API |
| C3 | 没有自动化抓取 | 存在 | 使用官方导出/接口 |

## 4. 手算示例

场景：个人账号，人在名单内地区；历史上有过一次跨国出差；用本人信用卡但账单地址填的是公司地址；一台笔记本 + 一台办公室台式机；Key 只放在 `.env` 里且 `.gitignore` 已覆盖；曾用过一个月中转，已迁回官方；没有自动化。

| 维度 | 答案 | 命中 | 计算 | 得分 |
| --- | --- | --- | --- | --- |
| 网络一致性 | 1,1,0,0,0 | 2 | 25 × 2/5 | 10.0 |
| 支付与身份一致性 | 1,0,0,0 | 1 | 20 × 1/4 | 5.0 |
| 账号使用模式 | 1,1,0,0 | 2 | 15 × 2/4 | 7.5 |
| API Key 卫生 | 0,0,0,0,0 | 0 | 15 × 0/5 | 0.0 |
| 第三方依赖 | 0,0,0,0 | 0 | 15 × 0/4 | 0.0 |
| 内容与自动化 | 0,0,0 | 0 | 10 × 0/3 | 0.0 |
| **总分** | | | | **22.5 → 中风险** |

优先补齐（按丢分排序）：N1（10 分）、P1（5 分）、N2/U2 并列（各 3.75 分）。

再看一个"看起来不严重"的场景：长期用中转、三个同事共用一个账号、Key 塞在前端、支付是老板的卡。

| 维度 | 命中 | 计算 | 得分 |
| --- | --- | --- | --- |
| 网络一致性 | 5/5 | 25 | 25.0 |
| 支付与身份一致性 | 2.5/4 | 12.5 | 12.5 |
| 账号使用模式 | 1/4 | 3.75 | 3.75 |
| API Key 卫生 | 3/5 | 9 | 9.0 |
| 第三方依赖 | 3/4 | 11.25 | 11.25 |
| 内容与自动化 | 0/3 | 0 | 0.0 |
| **总分** | | | **61.5 → 高风险** |

这个结果说明：**风险往往集中在"你以为是小事"的地方**，而不是你花了最多时间优化的地方。

## 5. 用脚本算（避免手算错误）

把答案写成 JSON：

```json
{
  "schema": "claude-account-guard/scorecard@1",
  "answers": {
    "network": [1, 1, 0, 0, 0],
    "payment": [1, 0, 0, 0],
    "usage": [1, 1, 0, 0],
    "api_key": [0, 0, 0, 0, 0],
    "third_party": [0, 0, 0, 0],
    "content": [0, 0, 0]
  },
  "declared_region": "US",
  "notes": "2026-10 自查"
}
```

```bash
python scripts/audit.py --scorecard scorecard.json
python scripts/audit.py --scorecard scorecard.json --json   # 机器可读，便于记录趋势
```

输出会给出每个维度的命中数与得分、总分、分档，以及按丢分排序的前三项。数组长度必须与条目数一致（5/4/4/5/4/3），取值只能是 `0`、`0.5`、`1`。

## 6. 使用节奏

- **首次**：完整做一遍，把不确定项列出来逐条查清。
- **每月**：只复算 K 与 T 两个维度（它们变化最快）。
- **变更时**：换网络环境、换支付方式、新增第三方依赖、加人共享——任何一项发生就重算一次。
- **事故后**：把事故前最后一次得分写进复盘，作为下一次的基线。

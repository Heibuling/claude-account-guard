# 封禁后 72 小时行动手册

## 0. 先判断你属于哪一类

| 现象 | 大概率性质 | 先看哪一节 |
| --- | --- | --- |
| 网页/客户端提示账号被限制、无法登录 | 账号级处置 | 全部（尤其 1、2 节） |
| API 返回 401/403、Key 提示无效 | 凭据被吊销或组织被限 | 1 节 → `api-key-hygiene.md` |
| 付款失败、订阅被取消 | 支付层问题 | `payment-and-identity.md` |
| 收到警告邮件但仍可用 | 风险提示 | 第 2 节自查，别等到第 3 节 |

**第一原则：先止损，再解释。** 大多数人在这个阶段花几个小时找"申诉话术"，而正确顺序是：把还在流血的伤口按住（吊销、下线、隔离），再整理证据。

**第二原则：不要销毁证据。** 不要删账号、不要清空邮件、不要卸载客户端、不要清理日志。你需要它们来说明时间线。

## 1. 0–24 小时：止损

按顺序做，每做完一项在时间线表里记一行（时间、动作、结果）。

1. **停止一切非必要调用**：把还在跑的脚本、CI、定时任务停掉。继续调用只会让用量曲线更难看。
2. **吊销全部可吊销凭据**：Console 里的 API Key 全部吊销（不是只吊销怀疑的那个）。吊销时间戳截图留档。
3. **下线中转/第三方 endpoint**：把 `base_url` 改回官方；如果这会让业务中断，先中断——中断可以恢复，"继续用别人的身份"不能。
4. **撤销所有会话**：账号设置里登出所有设备，改密码；如果开了额外验证，检查验证方式是否还是你的。
5. **隔离设备**：如果怀疑凭据泄露，把相关机器上的 `.env`、shell 历史、CI 变量做一次清理；新 Key 只在新环境使用。
6. **检查异常用量**：Console 用量页截图（按天/按模型），标出你认为不是自己的那一段。这是 B 级证据，也是判断"是否已被滥用"的依据。
7. **拉一条时间线**：从最近一次正常使用开始，按小时记。不知道的写"不确定"，不要编。
8. **确认封禁范围的表述**：把提示原文、邮件原文完整保存（截图 + 文本复制）。不同措辞对应不同申诉路径。

> 24 小时内不要做：反复提交申诉、在社交平台发情绪化长文、找"代申诉"、注册新账号"顶上"。

## 2. 24–72 小时：证据固化与合规判定

### 2.1 先做一个诚实的判断

在写任何申诉之前，回答三个问题（只写给自己看）：

1. 我是否使用过中转/共享账号/代付？
2. 我的接入网络、支付信息是否与申报一致？
3. 我的用途或自动化方式是否可能违反 Usage Policy？

**如果任一题答案是"是"**：你面对的不太可能是误封。此时正确做法是"承认 + 修正 + 请求恢复或导出数据"，而不是编造一套说辞。伪造材料的后果远大于账号被封（可能涉及欺诈）。

**如果三题都是"否"**：进入 2.2，按证据清单整理。

### 2.2 证据清单（A 级优先）

| 类别 | 具体材料 | 级别 |
| --- | --- | --- |
| 身份 | 注册邮箱的归属证明、身份材料（如平台要求） | A |
| 支付 | 银行对账单（遮盖卡号，保留姓名/地址/日期）、平台发票、订阅确认邮件 | A |
| 网络 | 公司 IT 出具的出口说明、宽带账单、出差行程 | A |
| 使用 | 设备清单、会话时间线、自己的调用日志（脱敏后） | B |
| 处置 | Key 吊销截图、base_url 修改前后 diff、停用脚本的提交记录 | B |
| 第三方 | 与中转服务的合同/账单（若曾使用，用于说明"善意使用"） | A |

**整理规则**：

- 用脚本把材料装进统一结构，别手工堆在下载文件夹里：
  ```bash
  python scripts/evidence_pack.py --init --dir ./evidence-pack      # 建 8 个编号目录 + 时间线模板
  python scripts/evidence_pack.py --add 02-payment ~/Downloads/statement-2026-09.pdf --dir ./evidence-pack
  python scripts/evidence_pack.py --build --dir ./evidence-pack     # 文本脱敏 + SHA-256 清单 + zip
  ```
  产物在 `evidence-pack/dist/`：`MANIFEST.md`（清单 + 发送前自查项）、`manifest.json`、`timeline.md`。
  **PDF/图片不会被自动脱敏**，清单里会逐条标出来，必须人工检查。
- 一个 PDF 一个主题，文件名写清楚：`01-payment-statement-2026-09.pdf`。
- 截图必须包含时间戳与可核验的上下文（URL、账号标识可打码）。
- 单独一份文本要脱敏时也可以直接跑：
  ```bash
  python scripts/redact.py -i statement.txt -o statement.redacted.txt --check
  ```
- 不要把完整 Key、完整卡号、完整身份证号放进申诉材料。

### 2.3 写申诉

用 `appeal-templates.md` 里对应场景的模板。三条硬规则：

1. **只写事实**，不写情绪、不写推测、不写"我怀疑是你们系统误判"。
2. **给证据编号**，正文里引用编号（`见附件 02`），让对方能核对。
3. **给一个明确请求**：恢复账号 / 说明原因 / 导出数据 / 关闭账号并退款（按你的真实意愿选一个）。

### 2.4 提交渠道

- 优先用平台官方的申诉入口（帮助中心 / 应用内支持 / 邮件里给的链接）。
- 一个渠道提交一次，保留工单号。
- 不要在多个渠道同时刷同一份内容——这会被当成滥用。

## 3. 72 小时之后：跟进、迁移、复盘

### 3.1 跟进节奏

| 时间 | 动作 |
| --- | --- |
| 提交后 48–72h | 若无回复，在原工单里追加一次简短跟进（不重复全文，只补充新证据与编号） |
| 7 天 | 仍无回复：换一个官方渠道提交一次，附上原工单号 |
| 14 天 | 接受结果。继续申诉的边际收益已经很低 |

**不要**：每天提交、换邮箱提交、用多个账号提交同一件事。

### 3.2 如果被驳回

- 检查是否有"新的、可核验的"材料；没有就停止。
- 询问是否可以导出数据（对话、文件、项目）。数据是资产，账号不是。
- 把结论写进复盘，不要反复消耗情绪。

### 3.3 迁移预案（无论申诉结果如何，都该做）

1. **清点依赖**：哪些服务/脚本/团队流程依赖这个账号。
2. **改配置**：`base_url`、Key 引用、模型名、重试与限额逻辑。
3. **选路径**：官方（人在名单内）→ 云厂商通道 → 企业版 → 本地可合法使用的替代模型。见 `third-party-risk.md` 第 6 节。
4. **灰度**：先跑非关键链路，确认延迟/成本/错误率。
5. **留档**：迁移 diff、账单、合同放进 `account-evidence/`。

### 3.4 复盘模板

```markdown
## 事故复盘 YYYY-MM-DD

- 现象：
- 首次发现时间 / 最后正常使用时间：
- 已确认的原因（六层中的哪几层）：
- 处置动作与时间戳：
- 申诉结果：
- 直接损失（时长/费用/客户影响）：
- 根因（配置/流程/人的决策）：
- 已修复项：
- 待修复项与负责人：
- 下次如何更早发现（监控/扫描/评审）：
```

## 4. 时间线表（直接抄）

| 时间（含时区） | 动作 | 证据/凭证 | 结果 |
| --- | --- | --- | --- |
|  | 最后正常使用 | 日志截图 | — |
|  | 发现异常 | 提示原文截图 | — |
|  | 吊销 Key | Console 截图 | 已完成 |
|  | 下线 base_url | 配置 diff | 已完成 |
|  | 提交申诉 | 工单号 | 待回复 |

## 5. 不要做的事（会显著降低你的可信度）

- **不要伪造材料**：改日期、P 图、编造发票、借用他人证件。这已经不是"账号问题"了。
- **不要隐瞒中转/共享**：账单和请求日志会暴露它；被指出隐瞒后，所有其他陈述都会被打折。
- **不要找人"代申诉"**：你需要交出账号信息给对方，这本身就是凭据泄露；且这类服务大量存在诈骗。
- **不要注册新账号"顶上"**：同一设备/支付/IP 上的新账号会继承关联风险，且可能被视为规避处置。
- **不要在公开平台发布带个人信息的申诉材料**：脱敏没做好会造成二次伤害。
- **不要相信"内部解封""包过"**：这类承诺 100% 是诈骗或二次收割。

## 6. 如果你的账号里还有重要数据

优先级：**数据 > 账号**。

1. 能登录时：立刻导出对话、文件、项目（用官方导出功能）。
2. 不能登录时：在申诉里明确请求"导出数据"，这比"恢复账号"更容易被满足。
3. 本地留一份：把导出的内容存进加密目录，别只放在云端。

## 7. 心理预期（很重要）

- 平台没有义务解释风控细节，也不会给你"证据清单"。申诉是**单向举证**，你只能提供材料，无法要求对方举证。
- 大多数申诉失败不是因为"话术不好"，而是因为**没有可核验的事实**。这就是为什么本项目的重点是"事前自查"而不是"事后话术"。
- 一个账号的损失是可承受的；真正需要复盘的是"为什么关键业务只依赖一个不可控的账号"。
